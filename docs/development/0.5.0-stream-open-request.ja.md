# Streamのopen request候補

C06の次の実装単位は、requestの型パラメータを残す内部Stream候補である。既存のclosed requestからopen serviceを閉じる処理に加え、Handler契約由来のrequest patternを保持する。BOCCHIが承認したType入口を使い、従来のgeneric入口も同じbindingへ渡す。

```csharp
configuration.Handlers(typeof(Read<>), DispatchFamily.Stream, typeof(ReadHandler<>));
configuration.Pipeline(typeof(Read<>), DispatchFamily.Stream,
    Stage.Hook(typeof(Keep<>)), Stage.Hook(typeof(Map<>)), Stage.Hook(typeof(Last<>)));
```

`ReadHandler<T>`にはZendiatorHandler属性が必要である。interfaceは明示されたserviceの型契約を検証するために使い、全requestやinterface実装を探索しない。stageのlist位置が順序を決める。request/itemへの型対応にはsymbol owner/ordinalと構造的な一致を使い、型引数の名前や並び順を仮定しない。例えば`Handler<U,T>`が`Read<T,U>`を担当する場合、内部候補の2番目の引数がitem型となる。

可変parameter、固定型、配列、構築generic型、反復parameterを区別する。Handlerの全parameterはrequest patternから決まる必要がある。item契約もrequestのitem patternと一致しなければならない。stageは同じrequest/item patternから型を構築する。生成用parameter名はsymbolのdisplay partに基づいて置換し、ユーザーの名前や同名型への文字列置換をしない。

request、handler、stageの対応済みparameter constraintsを合わせ、内部generic候補のwhere句へ明示する。class/class?、struct/unmanaged、notnull、new()、base/interface、他parameterへの制約が対象となる。追加stageのconstraintsは内部候補の適用範囲を狭めることがある。例えばclass?とclass,new()を合わせた候補はclass,new()となり、任意のvalue itemで利用できるとは扱わない。primary constraintの矛盾、無関係なclass base constraints、直接parameter制約の循環は診断する。固定型/構築型に対するconstraintは現在のsymbolから成立を証明できる場合のみ採用し、証明できない場合や投影に外国のparameterが残る場合は拒否する。

closed入力は既存GenericConstraintsで実引数を確認する。open内部候補を閉じて利用する際は生成されたwhere句もcompiler/CLRの型閉鎖契約となる。nullable dependent constraints、すべての相互依存やconstructed constraint推論を証明したとはしない。制約domainだけを根拠にopen pattern同士をdisjointと推測しない。

同じcompositionで重なり得るopen/closed明示登録は拒否し、source位置と元の位置を診断する。型構造のunificationで反復parameterや固定型の不一致を扱う。closed特化優先や宣言順での採用を導入しない。診断は追加位置が参照する元routeにも投影し、片方だけが候補として残らないようにする。同じserviceへ閉じるhandler/stageの重複も従来どおり拒否する。

internal候補classにgeneric parameterとwhere句を持たせる。fixed int itemのopen class requestでF1/Map/F2等の既存条件を満たす場合はfusion候補、可変itemやwrapper付きの適合形はtyped canonical候補となる。型を閉じた明示登録は同じ型対応の後で既存projectionへ渡し、fusionが適合すれば優先する。generic canonicalをintでJITしただけでgeneratorのfusion選択をやり直すruntime分岐は追加しない。

DI resolverと列挙実行bodyは変更しない。serviceは通常のtyped解決で借用し、scopeは列挙とcleanupより長く生存する必要がある。handler/sourceの開始とhookの初回到達を遅延させ、service/providerをcursorがdisposeしない。source cursorとlinked tokenの所有終了、wrapper上流の置換request/tokenも既存の契約を使う。

この候補は未検証で、public Stream登録とZEN0037の遮断を維持する。新しいpublic dispatch API、reflection dispatch、Configure<T>の必須化は追加しない。Type入口のopen bindingはStreamのこの内部backendが対象であり、他familyのopen適合をこの変更だけで宣言しない。C06/C07全体、open containing type、ref-like request/item、session、値型receiver、alias、すべてのconstraints/context、複数/同時/再列挙Open、他provider、public採用と性能は残要件である。
