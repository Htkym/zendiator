# 途中型変更とwrapper/sessionの公開接続

BOCCHIが受け入れた内部typed integrationのclosed `large-wrapper-session` fixtureを、通常の`AddZendiator`と公開`IZendiator.StreamAsync`につなぐ。単一family・閉じたrequestを対象とし、既存のCreate・cursor・DI所有契約を使う。

sourceは`int`、内側の同期Mapは`int → LargeItem`、wrapperは`LargeItem → LargeItem`、外側の非同期Mapも`LargeItem → LargeItem`である。`LargeItem`は既存の128B structを再利用する。公開戻り値は`IAsyncEnumerable<LargeItem>`、両cursorのCurrentもLargeItemとし、内側sourceはint、外側sourceとUpstreamはLargeItemを保持する。

期待snapshotは宣言された`StreamPipeline<BigRequest,LargeItem>`とhandler/session・Hook/Wrapperの組を記録する。実際のDIキーは閉じた4factory型であり、session receiverをserviceとして登録しない。factoryはscopeが所有し、各segmentのsessionとsourceは既存cursorが終了する。新しい契約判断は追加しない。

## 今回の受入条件

- 正常な公開経路を1回だけ列挙し、値701、128B final型、両segmentの保持型、通常snapshot照合、closed DI登録を確認する。
- 隣接Mapとwrapperの型不一致をZEN0026で拒否し、公開生成物を出さない。
- 最終生成物は各compile.jsonのsources一覧を基準に保存する。既存helperの証拠は過去の内部検証として区別する。
- sessionはB・W・A・Hの順で取得し、source・H・A・W・Bの順で終了する。scope終了前のfactory Disposeは0、終了後は4とし、scopeがsessionを再終了しない。

公開ゲートはclosed intから値型へ変換する同期Map・同型wrapper・同型非同期Mapの2segment構成、4つの同期所有factoryに限定する。既存typed emitterは変更しない。openとの組合せ、複数family、内部cleanup全matrix、JIT/PGO、性能測定は今回の検証対象へ広げない。時間判定HOLD、後日の最適化と再検証、commit/push保留を維持する。

BOCCHIはv17を受け入れた。ゲートはitemのサイズやLargeItemという型名を条件にしない。所定の段構成・型接続・所有方式を満たすclosed値型itemを受け入れ、128B LargeItemはその代表検証である。任意の値型・サイズについて検証を完了したという意味ではない。

限定検証の結果と実diffは今回の証拠rootへ保存し、Libraryの同一artifactへ新しいversionとして保存・読み戻し検証した後にBOCCHIへ返す。

## 限定検証の結果

WindowsのSDK 10.0.300／runtime 10.0.8、Releaseで新しいFactだけをRTK経由で1回実行し、1件が通過した。consumer compileは正常と隣接型不一致の2回、公開外側列挙は1回、その内部のOpenと内側列挙は1回である。公開正常生成の診断は0、compiler warning/errorも0だった。CS8019 Hiddenはrawに保持する。

公開`IAsyncEnumerable<LargeItem>`から701を取得した。実DLLの両cursorのCurrentと`_current`はApp.LargeItem、内側`_source`は`IAsyncEnumerator<int>`、外側は`IAsyncEnumerator<LargeItem>`で、Marshal.SizeOfは128だった。consumerはLargeItemを直接受け取り、Valueをlongとして読み、itemをobjectへ変換しない。生成cursorのIL全走査やcopy量の測定は行っていない。

通常登録のsnapshot照合を通過し、閉じた4factory型がScopedで登録され、4session receiverはDI登録されなかった。source開始1、Move2、Current読取り1、source Dispose1を確認した。session取得はB:1・W:2・A:3・H:4、終了はsource・H:4・A:3・W:2・B:1だった。distinct sessionは4個、scope終了前のfactory Disposeは0、終了後は4で、session Disposeは4のままだった。

wrapperがintを宣言する隣接型不一致は、`Stage.Wrapper<BigWrapper,BigWrapperFactory>()`をanchorとするZEN0026で拒否した。compile.jsonのsourcesにはcatalogと通常補助sourceだけがあり、公開facadeとcanonical cursorは生成されなかった。

今回の最終生成物は`consumer-results/public/compile.json`の5source、拒否側は`consumer-results/interval-mismatch/compile.json`の2sourceを正本とする。`historical-internal-128B-reference`は受入済み内部helperの履歴証拠であり、今回の生成物へ混ぜない。既存内部Factは正常closed側の公開診断期待だけを修正し、旧matrixは実行していない。既存typed emitter、shared registrar、所有処理は変更しなかった。
