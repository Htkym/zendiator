# Stream候補の生成接続と診断境界

C05の候補実装は、既存のroute backend選択とroute描画に、検証済みの閉じたclass request／handler／hook、int item、Filter→Map→Filterの融合経路と、新契約から直接生成するcanonical経路を接続する。対応済み融合経路を優先する。canonical側もinternal helperとしてのみ生成し、public登録とinterceptorを有効にしない。ZEN0037を維持する。

接続判断は次のとおりである。

| 入力 | 候補出力 | 診断と残る作業 |
|---|---|---|
| 対応済み経路と一意な構成 | 共通backendでlowerし、共通rendererが描画した候補を出力 | ZEN0037でpublic登録を遮断。性能と採用判断は未完了 |
| 閉じたclass receiverの任意順の同型item hook、高度wrapper混在 | typed canonical cursorとupstream factoryを生成 | ZEN0037でpublic登録を遮断。新しい候補の意味論・性能・採用判断は別に確認 |
| 未対応の値型receiver、session、open binding、extern aliasなど | 候補なし | CanonicalPendingと既存診断。未実装を明記 |
| 型不一致、不正なlist、未対応のopen型など | 候補なし | 既存のsource location付き診断。compiler-owned errorはcompilerに残す |
| 構成のmarker／key／namespace、または候補出力identityの競合 | 候補なし | 競合を診断し、最初の構成も生成しない。重複の追加locationを維持 |

canonical候補は旧adapterやテストreferenceを呼び戻さず、handler、各hook、wrapperの新しいtyped契約を直接呼ぶ。item型は各区間で同一であり、list順、false短絡、Currentの単回取得、lazyなservice解決、借用DI、所有cursorの終了と通常の例外置換を実装する。各Move/Disposeはその呼出し元のcontextから始まり、hook間にasync adapterを追加しない。

wrapperを越えてhookを移動しない。生成upstreamのOpenは指定request/tokenを保存する新しいenvelopeを返し、列挙ごとに独立cursorを作る。wrapperは上流0回、複数回、列挙時にOpenできる。wrapperの出力cursorはconsumer側が所有し、wrapper自身の借用serviceをdisposeしない。wrapperが直接Openを返す場合、frameworkのGetAsyncEnumeratorにouter tokenを再適用しない。opaque本体のcleanupを一般に保証するとは説明しない。

CanonicalPendingを実装済みfallbackとは扱わない。diagnostic suppressionは診断の表示だけに作用し、backend選択、候補ソース、public登録の可否を変更しない。

原計画C05の同じ新契約canonical生成を、上記の閉じたclass receiverの候補範囲に実装した。実行前の候補であり、C05全体の完了や本番採用とはしない。C06のopen generic／DI scope、constraintsの全組合せ、session/値型receiver、全C07、wrapperを含む全graphの同値性、性能測定、本番採用を後続に残す。providerは借用して保持するため、破棄済みscopeやfactory overrideの契約確認はC06へ依存する。

先の代表12件の保証範囲も維持する。開始前取消ではhandlerが未到達なので、そのtoken同一性は未観測である。api-suppressionはTask.Runへの非継承確認のみであり、取消済みtokenのcallback観測だけではlinked解放の独立証明にならない。
