# Stream候補の生成接続と診断境界

C05の候補実装は、既存のroute backend選択とroute描画に、検証済みの閉じたclass request／handler／hook、int item、Filter→Map→Filter経路を接続する。実行テンプレート、token、context、cleanupの処理は変更しない。候補はinternal helperとしてのみ生成し、public登録とinterceptorを有効にしない。ZEN0037を維持する。

接続判断は次のとおりである。

| 入力 | 候補出力 | 診断と残る作業 |
|---|---|---|
| 対応済み経路と一意な構成 | 共通backendでlowerし、共通rendererが描画した候補を出力 | ZEN0037でpublic登録を遮断。性能と採用判断は未完了 |
| 有効だが候補の範囲外の順序、item型、高度wrapperなど | 候補なし | ZEN0037で同じ新契約のcanonical生成が実装待ちであることを説明 |
| 型不一致、不正なlist、未対応のopen型など | 候補なし | 既存のsource location付き診断。compiler-owned errorはcompilerに残す |
| 構成のmarker／key／namespace、または候補出力identityの競合 | 候補なし | 競合を診断し、最初の構成も生成しない。重複の追加locationを維持 |

canonical生成待ちを、実装済みのfallbackとは扱わない。旧adapterやテストreferenceへ自動的に切り替えず、未対応経路を省略して成功扱いにしない。diagnostic suppressionは診断の表示だけに作用し、backend選択、候補ソース、public登録の可否を変更しない。

原計画C05には同じ新契約のcanonical生成とfallback snapshotsも含まれる。今回の接続・診断境界だけではC05全体の完了としない。C06のopen generic／DI scope、constraintsの全組合せ、全C07、wrapperを含む全graph、性能測定、本番採用を後続に残す。

先の代表12件の保証範囲も維持する。開始前取消ではhandlerが未到達なので、そのtoken同一性は未観測である。api-suppressionはTask.Runへの非継承確認のみであり、取消済みtokenのcallback観測だけではlinked解放の独立証明にならない。
