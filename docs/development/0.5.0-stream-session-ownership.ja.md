# Stream列挙固有sessionの生成と所有権

既存`IOwnedSessionFactory`／`IAsyncOwnedSessionFactory`、`IBorrowedSessionFactory`／`IAsyncBorrowedSessionFactory`と`BoundSessionModel`、Stream session scheduleを生成候補へ接続する。新しいfactory APIやgeneric orchestrationを追加しない。factoryとstatelessサービスはDI所有のままで、owned結果だけを列挙が所有する。Streamのowned cleanupは`IAsyncDisposable`である。public登録はZEN0037のままにする。

最初のMoveまでfactory解決・session生成・source取得を遅延する。session hookはlistの外側から内側、最後にhandler sessionを開始する。正常終端や開始後の本体失敗ではsessionをDisposeまで保持する。Disposeではsource、取得順の逆順にowned session、linked tokenを終了する。開始途中の失敗では取得済み結果だけを各1回終了する。nonnull成功だけが所有権を移す。借用sessionやDI serviceはcursorからdisposeしない。cleanupはdetach後に順に行い、内側cleanupの失敗でも外側cleanupを続け、最後に投げた例外を保つ。

限定候補はclosed public request、class handler/hook、class factoryのplain Stream経路。wrapperとsessionの組合せ、open session、型変更との直積は今回の生成候補へ広げない。stateless候補の生成bodyは既存分岐を維持し、session field・factory call・session cleanupを出力しない。allocationやtimingの測定は行わない。

限定検証は1Fact、session／statelessの2SG入力・2consumer emit。session入力を正常再列挙と内側handler factory失敗の2profileで使う。正常は同じenvelopeで各backend2列挙、失敗とstatelessは各backend1列挙、合計8列挙・3比較。独立referenceと実生成DLLを比較する。正常では3sessionの開始順、別session identity、最初のMove前の無生成、async factoryのpending・GetResult1、終端後も保持、source→逆順session終了、DI scopeでのサービス終了を確認する。失敗ではhook session2個だけが逆順に終了し、handler/sourceを未取得として扱う。stateless入力はsession生成0と追加のsession生成siteなしを確認する。既済み取消／wrapper／型制約の直積を追加しない。

Release build1回・指定Fact1回。見込み240秒・総上限600秒・remote420秒・回収終了枠120秒。private CPU Colabを使い、SharpDepsのlocal枠は使用しない。重大仕様判断・初回失敗・timeout・pins/件数不一致・所有runtime終了不確認では停止して返す。自動修正・再試験はしない。元TRX・実diff全文・manifest・終了確認をLibraryへ保存し、実読み戻し後にBOCCHI最終レビューへ返す。commit/push/Actions/public解除は含めない。

plain単位はBOCCHI受入済み。次のwrapper境界単位では既存wrapper segmentにsource factoryと各hook factoryを結び、handler factoryをhandler sourceの区間だけで使う。Wが上流を開かなければ内側sessionを生成しない。同じOpenが返すenvelopeを別cursorで列挙すると、それぞれが新しい内側sessionを持つ。内側cursorは自身のsourceとsessionだけを終了し、外側W・hook sessionは外側Disposeまで保持する。wrapper bodyの値・retry・tokenを書き換えない。

wrapper所有境界の検証は新1Fact・1生成入力・1consumer emit・2profile。Openなしと、Open1回で同じ上流envelopeを2回列挙する場合を比較する。各backendの外側2列挙・内側2列挙、合計8列挙・2比較。outer hook→Wとinner hook→Hの生成順、別session実体、内側終了後も外側2sessionがlive、source→H→inner hookとW→outer hookの所有分だけの終了、DI scopeのfactory終了を確認する。同期owned factoryと完了済みcleanupを使う。既済みwrapper値・retry・tokenの直積やplainの再検証は追加しない。見込み240秒・総上限600秒・同じ初回停止条件を適用する。

wrapper受入時点のC11残件はcleanup自身の実pending／失敗時の継続、borrowed factory結果の実寿命、open session／open型変更、型変更とwrapper/sessionの接続、large struct、総allocation／JITコピー、allocation/timingの実測、public採用判断。ここまでの実行証拠からこれらを証明済みとは呼ばない。commit/push/Actions/public解除も保留する。

次のcleanup／borrowed単位は既存生成bodyを使う証拠接続とし、製品コードを変更しない。ownedのinner／outer hook2個と、実DI scopeが所有するhandler instanceを返すborrowed factoryの短い列を使う。新1Fact・1生成入力・1consumer emit、pending成功と内外cleanup両失敗の2profile、reference／生成DLLの合計4列挙・2比較に固定する。両owned cleanupは`ContractOnce<bool>.Void`の実IValueTaskSourceでpendingを作る。innerの完了／失敗までouter呼出し0を確認し、outerもpendingにして各GetResult1を確認する。両失敗時は最後のouter例外instanceとfaulted状態を保つ。再Disposeでは呼出しとGetResultを増やさない。borrowed結果は実DIから取得した同一instanceであることを確認し、cursor終了時は破棄0、DI scope終了時は結果1・factory3の終了を独立観測する。wrapper／Open／型変更／取消の直積は追加しない。

この証拠の検証見込み240秒、総上限600秒、remote420秒、回収終了枠120秒。private CPU Colabの1build・1指定Factのみとし、初回失敗／timeout／終了不確認は停止する。対象外のopen／型変更接続・large struct・allocation/timing・public採用とcommit/push/Actionsは残件のままにする。
