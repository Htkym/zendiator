# Zendiator 0.5.0 の開発台帳

第3版「Zendiator 新仕様と共通融合および生成処理の改善計画」をタスク単位で実装し、限定検証、ローカルコミット、親レビューを行う。計画書は `.local/0.5.0/Zendiator_Stream_Improvement_Plan.md` に保持する。220,185 bytes、SHA256 は `7898BF2AE3A44C36EB6E6FF8DE1E993190B8E719ED59328A25B1C9F225F8C045` で、指定された第3版と一致した。

## 開始点と現状

未コミット変更がない状態で `main` に切り替え、`git pull --ff-only origin main` を実行した。開始 SHA は `b5b109281166a577c1d3d5b0d1349f50a40366cf`、作業ブランチは `feature/0.5.0`。追加 worktree や補助ブランチは作成していない。

唯一の性能基準 H0 は `1c41d2b105073d2dc9be2c0e8684fdce2fa11f55` の今回の360ケースである。開始 SHA との差分は19ファイルで、製品ソースの変更は生成コードのバージョン表記2か所。テストの変更は既存 ValueTask を一度だけ Task 化する修正であり、ほかは公開文書、バージョン、集計表、benchmark 証拠の書式変更である。差分全文は `.local/0.5.0/baseline/implementation-start.diff` に保存した。

既存の DirectCall、struct continuation、pooling builder、等価 model、出力 cache を出発点とする。旧API互換性は必須ではないが、例外、token、DI所有権、順序、ValueTask単消費を新契約で定義する。Handler属性による発見、明示順序リスト、Send/Streamの共通hook融合、incremental前段、Analyzer/CodeFixを対象にする。任意wrapperの意味は推測して書き換えない。

## P00 の実装と証拠

`benchmarks/Zendiator.UseCaseBenchmarks/verify_baseline.py` を実装した。manifestで指定した既存ファイルのhash、raw ZIPの全inventory、case別のworkloadと統計、除外されたiterationのidentity、394件のbenchmark gate、保存されたruntime/consumer DLLを読み取り専用で照合する。欠損、別SHA、異なるworkload、重複iteration、改変binaryを失敗として扱う。

P00の実データ照合結果は、Send125 / Features55 / Stream120 / Relay60、raw4,320 / valid4,042 / 除外278、各群のgate394、rawファイル4,404と内蔵inventory1、保存DLL720で一致した。既存の全360ケース実行実績17,255.54761秒も照合した。今回の照合ではruntime/consumer以外のbundleファイルは再hashしておらず、保存された既存の全bundle監査を参照する。

新規7テストと既存artifact/driverテストを合わせて36件実行し、34件成功、プロセスfixture2件は既定のopt-outによりskipした。基準資料を変更しないこともsynthetic fixtureで確認した。製品コードの変更がないため、このタスクでは.NET build、全suite、package、AOT、性能測定を実行していない。

## 受入条件

新契約の正しさを性能より優先する。canonical N0 と候補 N1 のtraceを一致させ、旧H0からの移行比較は別系列にする。候補測定前にhot経路の実用差閾値を `max(controlの2%, 2 ns/op)`、IL増加10%、hot native code増加15%、warm生成/build時間増加10%のレビュー境界として記録した。非対象経路への追加heap allocationと追加per-item allocationは許容しない。

coldの相対許容差は5%を初期値とし、絶対時間、主要case、必要launch数、同時区間の分析方法はP03のcontrol-only pilotで候補結果を見る前に確定する。確認は5以上の独立launchと95%信頼水準を出発点とする。Analyzer/IDEの予算と最低hostはN01で固定する。未確定値を埋めたことにはせず、依存が完了するまで性能採用判定へ進まない。

重い測定は排他とし、準備からcleanupまで1枠55分以内、50分以降は新caseを開始しない。screeningは8〜16case程度から始める。AIによる反復監視は行わず、機械の完了通知か見込終了後に回収する。新しい重い測定枠はまだ設定していない。
