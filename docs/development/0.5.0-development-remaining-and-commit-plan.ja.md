## 次に選ぶ本開発単位

**open requestのowned handler/session＋型変更Mapを、単一plain segmentの通常登録と公開StreamAsyncへ接続する。** C06/C10/C11の既存内部成功fixture `open-session`を使い、wrapperや複数familyを同時に広げない。

既存宣言は`Handlers(typeof(OpenRequest<>), Stream, HandlerEntry.Session(typeof(OpenHandler<>), typeof(OpenHandlerFactory<>)))`と、`StreamPipeline(typeof(OpenRequest<>), typeof(OpenFinal<>), Stage.Hook(typeof(OpenMap<,>), typeof(OpenMapFactory<,>)))`。handler/sourceはT、Map/finalはOpenFinal<T>、factoryはrequestと確定receiver契約から閉じる。既存内部比較の値7、M:1→H:2取得、source→H:2→M:1終了、factory2個のscope所有を再利用する。

公開の最小契約は、非generic IZendiator/Zendiatorと、requestから推論する`IAsyncEnumerable<OpenFinal<T>> StreamAsync<T>(OpenRequest<T> request, CancellationToken cancellationToken = default)`である。fixtureのwhereは`T : class, new()`で、一般規則として固定しない。finalとwhereはbound model、snapshotのrequest/final/receiver/factory定義は現在symbol、実行DIキーは閉じたfactory型から生成する。名前・ordinal・文字列解析から型引数を推測しない。owned receiverをDIへ登録せず、TryAddで利用者の既存lifetimeを保持する。

必要な変更は、open登録metadataに明示finalとhandler/stage factory定義を保持し、既存borrowed用registrarがfactoryを落とさずliteral宣言のsnapshotを再現すること、publicゲートが所定のsingle Map/session形状を受け入れることである。既存Create/cursor・型閉鎖・cleanup/DI所有契約を使う。新しい一般公開契約を必要とする差が見つかったら、その適用前に論点だけを返す。

この単位の終了条件は、通常登録から公開入口を有効な1型引数で閉じる成功例1回、公開final/Current/sourceとclosed DIキー・宣言snapshotの一致、session2個の一回cleanupとfactory2個のscope終了を確認すること。拒否は未決定factory引数の既存ZEN0035/source anchorを公開接続でも維持する1入力に絞る。compile.json sourcesを最終生成物の正本にし、生成source/DLL/trace/実diffを保存・読み戻す。旧内部成功/cleanup/制約matrix、v12借用公開経路、性能測定を再実行しない。

この資料は次単位の提案であり、実装・test開始の承認や完了ではない。

## commit候補と公開前条件

v18の後、BOCCHIはopen owned Map公開接続の実装と、ここまでのレビュー済み成果を一つの統合commit候補にまとめるよう指示した。下表はv18時点の分割案であり、今後4つの過去版を再構築する要求ではない。統合候補は最終treeの実diffとsource pinを正本とし、無関係ファイル・raw・DLL・秘密を除外する。最終compileと共有registrarのSend/multi影響に必要な限定compileを確認してLibraryへ返す。commit/push保留は維持する。

既存source manifestの版境界を使い、現在の全ファイルを一括stageしない。後続の公開接続で同じbinding/model/registrar/既存テストの診断期待を編集しているため、ファイル名だけで独立commitへ分けられない。以下は依存順の候補で、各candidateの独立compileは今回未確認である。

共有sourceのhunkを安全に再構成できない場合は、内部拡張と公開接続を一つの依存した機能commitへまとめる。分割数のために中間commitを破損させない。候補ごとの実diff、source pin、既存実行版との対応と限定検証結果をBOCCHIが確認するまでcommitしない。既存未pushのHEADも勝手に送らない。

featureへの公開前条件は、候補境界の確定、mixed fileと既存fixture診断期待の整合、必要最小の候補build/接続確認、共有registrarの既存Send/multi出力への影響確認、受入れ証拠と最終sourceの対応、秘密/無関係ファイルを含まない実diff、BOCCHIのcommitレビュー通過である。通過済み全matrixを再実行する条件ではなく、分割・新変更で生じた未確認だけを検証する。

ユーザーはBOCCHIレビュー済みcommitのfeature/0.5.0への通常pushと検証Actionsを承認済みだが、現在の委任ではcommit/pushを保留している。main push/merge、force push、tag、release、NuGet公開は含まない。feature commit公開と0.5.0 release完了条件も別で、releaseには原計画の残件・採否・package/Analyzer/CodeFix/UX/再現性を閉じる必要がある。
