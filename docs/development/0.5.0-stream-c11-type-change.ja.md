# C11 型変更mapのAPI・typed接続・限定検証

原8.10とC11に沿い、`StreamPipeline<TRequest,TFinal>(Stage...)`で最終item型を明示する。`IStreamRequest<TSource>`と既存`IStreamRequestHandler<TRequest,TSource>`はhandler内側itemを表し、この契約は変更しない。型変更routeの最終型をrequest markerから推測しない。既存Pipelineは同型経路のままで、型変更mapには明示StreamPipelineを要求する。public登録はZEN0037のままである。

新専用契約は`IStreamItemMap<TRequest,TIn,TOut>`と`IAsyncStreamItemMap<TRequest,TIn,TOut>`。後者はValueTask<TOut>を順に1回だけawaitする。handler source、最終型、各stage Input/Outputをnullable-awareなidentity・C#名・value-type情報としてtyped IRで独立保持する。list順に接続し、wrapperの入出力は同じ境界型である。nullabilityを落として互換扱いしない。

生成cursorはsource側`IAsyncEnumerator<TSource>`と最終typed Currentを分け、mapごとに別typed localを作る。objectのitem経由、dynamic、boxing、型キャストで接続不一致を回避しない。DIサービス取得に必要な既存object戻り値からreceiver interfaceへのcastはitem flowとは区別する。新IRは既存typed canonicalとwrapper区間へ接続し、別のgeneric orchestration基盤を追加しない。

最小検証は新1Fact・5入力。成功1列はint7→string? null→long70のsync/async mapsで、generic sync mapのstruct制約をinput intから閉じる。async mapは実IValueTaskSourceのpendingとGetResult1、独立reference／生成DLLの値・順序・source Dispose1を確認する。拒否4例はstage input、wrapper境界、nullable→nonnull接続、明示final型の不一致を正式StageTypeMismatch＝ZEN0026で拒否し、candidateを生成しない。ID・Error severity・該当source位置を同じ診断で確認する。入力不一致に伴う最終型不一致の追加診断は許容する。ZEN0035は未対応生成形状の診断であり、この接続不一致とは区別する。

成功consumer1、診断入力4、SG入力/emit5、runtime2列挙1比較。nullableとconstraintsは上の変更経路に限る。生成Current型がlongで保持8 bytes、source cursor型がint、awaiter/処理中item fieldsに不要なobject保存がないことをreflection/生成source/選択methodのILで確認する。ILは生成変更経路だけをdecodeし、item box/unbox/object経由を調べる。既存取消/retry/Open/DI/制約matrixは再試験しない。

Release build1回・指定Fact1回、見込み240秒・総上限600秒・remote420秒・回収終了枠120秒。private CPU Colabの既存承認範囲を使い、SharpDeps local枠は使わない。重大判断が原契約から決められない場合、初回失敗、timeout、pins/診断/件数/終了不一致は停止して返す。自動修正/再試験をしない。機能内の小差分ごとの親承認待ちは挟まない。

今回のprototypeはclosed public request/item、borrowed class receiversの変更列である。open request pattern、session所有権、large struct/任意wrapper列、性能、公的採用は別の残件とする。既存handler契約を使うため移行はfinal型のStreamPipeline明示と3型引数mapへの変更で足りる。C11全体のsessionや測定はこの型変更単位で完了とは呼ばない。commit/push/Actionsは含めない。
