# 0.5.0 通常Stream登録・dispatch接続の次工程

2026-10-14。現候補の開発実装としての[暫定採用](0.5.0-stream-typed-integration.ja.md)を受けた次工程の提案である。追加測定、公開登録解除、commit／push／Actionsはこの記録では実施しない。

## 原計画と現在の実装

原第3版のC05/G03は、同じ新契約のcanonical生成と未対応shapeの明確な診断を要求する。U01は実APIによる最小Stream例のcompileを要求する。内部のStream候補、同期seed corpus、C10のasync hook、C11の型変更・sessionの有限検証は既存証拠を再利用する。C09/C12の最適化・性能再検証は後日扱う。

`CanonicalStreamEmissionNormalizer`は有効graphを候補へ接続するが、public登録は保留と明示している。`CanonicalStreamFallbackEmitter`が出す入口はinternal static Createであり、通常の登録・dispatchから使う公開入口ではない。`CompositionSelectionDiscovery.Report`にはSend系で受入れ済みのbackendと実登録call siteに限定したZEN0037抑制があるが、Stream用の受入れはない。`AddZendiator<TComposition>`本体は未接続callを失敗させるbootstrapである。これを無条件に成功させる変更では解決しない。

## 次の最小機能単位

named compositionから既存Stream候補へ到達する、通常DI登録とtyped StreamAsync dispatchを接続する。最初はclosed reference-type request、int item、borrowed class handler／同期Filter→Map→Filterの単一pipelineに限定する。既存C10/C11の有限fixtureを再展開せず、公開入口という新しい境界を検証する。open generic、owned session、型変更、opaque wrapper、複数familyを含むcompositionは、この単位の公開受入範囲へ自動追加しない。

必要な変更は次の3点である。

1. 既存のnamed composition生成方式に沿って、Streamの登録call siteと公開出力を結ぶmodel／projectionを追加する。composition全体のroute対応、出力名の衝突とcall site一意性を確認し、未対応routeの黙った省略を防ぐ。
2. marker namespace.Generated.Marker名のIZendiator／Zendiatorに、StreamAsync(Request request, CancellationToken cancellationToken = default) → IAsyncEnumerable<int>を生成する。F1→Map→F2で選択済みの融合候補のCreateへ薄く接続し、別backendへ置き換えない。registrarは現named compositionのScoped＋TryAddを踏襲し、既存登録を上書きしない。利用側は列挙終了までscopeを保持し、cursorはborrowed serviceを破棄しない。
3. ZEN0037解除の条件を、契約受入れ済みのshapeと実際に生成・接続した登録call siteの両方へ限定する。未対応・不正・衝突shapeのsource診断を維持し、public APIの使用例を実コードで追加する。

## 公開登録を解除するための契約受入条件

開発実装の暫定採用と別に、実装前レビューで次を確定する。

- 公開型／namespace／StreamAsyncのsignature、最終item型、composition markerと登録call siteの対応。request二重markerや新たなStableフラグを要求しない。
- dispatchとGetAsyncEnumeratorまでのlazy境界、first Moveでのresolve／HandlerStart、requestとAPI token／列挙tokenの伝播、全件消費と早期終了のcleanup契約。有限候補の既存証拠と公開経路との対応を説明する。
- borrowed handler／stageはDI scopeが所有し、cursorがserviceを破棄しないこと。生成registrarのlifetimeと、provider／scopeを保持する責任を確定する。
- composition内に未対応routeがあれば、それを省略して登録成功と見せないこと。unsupportedには同じ新契約で対応済みのcanonical経路か明確なsource errorを使う。

BOCCHIはv8計画の契約レビューで、この限定shapeと上記公開入口、Scoped＋TryAddを受け入れた。request null検査はdispatch時、token合成・取消検査・handler開始はfirst Move時、hook resolveは到達時とする。公開methodにはSendの同期取消検査を持ち込まず、source／linked tokenの終了は既存cursorに任せる。単一pipelineでcomposition全体の対応確認と実登録call siteが揃う場合だけZEN0037を解除する。open／owned／型変更／wrapper／複数family等は公開登録を保留する。

時間HOLDの解除を公開契約受入れの代わりにせず、ZEN0037全体の抑制や原C08/C10/C11の完了をこの小単位の終了条件にしない。上の契約判断がこの機能単位の実装・最小検証の開始条件を満たした。

## 最小検証と終了条件

限定検証では、通常AddZendiator<TComposition>からDIで生成IZendiatorを取得する実consumerを1形状だけcompile／実行する。内部Createへの直接呼出しやreflection helperを使わない。default tokenで全件消費、異なるAPI／列挙tokenで全件消費、早期終了の計3列挙を上限として、lazy開始、期待出力、token伝播、source終了、cursor終了とDI scope終了の所有区分を照合する。新しいasync／generic／wrapper matrixや性能測定は追加しない。

診断検証は未対応routeを含むcompositionの拒否を1入力、登録／出力identity衝突の拒否を1入力に限定する。source locationと既定診断を確認し、通常入口を成功と誤認させない。既存finite意味論・seed corpusの結果は証拠参照で済ませる。

終了条件は、受入れ済み限定shapeが実登録・public dispatchを経由して期待値と終了契約を満たすこと、consumerにcompiler warning/errorとSG診断がないこと、拒否2入力のsource診断が期待どおりであること、生成source／実diff／限定結果をレビュー可能に保存すること。公開対象を広げる条件は次の機能単位へ残す。
