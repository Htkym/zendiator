# Streamのfactory・callback・downstream context境界

原計画8.2.1/C07とD03の共通modelに従う。同期callbackをstageごとのasync adapterで囲まない。同期factory/hook/getterのambient再代入はそのMove内の後続へ見え、各Move/Disposeの返却では通常のC# async境界によりcallerの値を保つ。次Move/Disposeは新しいcallerのcontextで始める。native async producer/wrapper自身の変更は自身の継続に残り、外側へ変更を転記しない。ExecutionContextは共有objectのdeep copyやrollbackではない。

## 受入れ済み観測との対応

| 原契約の境界 | 既存の受入れ証拠と範囲 |
| --- | --- |
| factory H→handler→Get/Move | 4d5b438のsame-pending-contextでfactory:H.enterの変更をH/Get/Moveが観測。実SynchronizationContext identityも確認。 |
| getter/factory F1→F1→Map/F2 | 4d5b438のnone-sync-context/same-pending-context。17134f7のlong canonicalでF1はfactory、Map/F2はcallbackを観測。 |
| 次Moveのcaller | 4d5b438のconsumer caller-a/caller-bと17134f7の次Move@caller。前Moveのcallback値を持ち越さない。 |
| native producerの継続／caller返却 | 4d5b438の実pending source helperでenter/resumeは自身の値、Current/downstreamは外側Moveの値。Move/Dispose gateを各1回消費。 |
| wrapper sync／native async | 9432396のdirect/early-break。Hはwrapper-syncまたはwrapper-async、外側F2はwrapper-sync。wrapperを勝手にasync化しない。 |
| SynchronizationContext | 4d5b438の同期/実pendingと9432396のcanonical同期instance比較。pendingで任意context/threadを保持する保証は追加しない。 |

| startup／failure／cleanup | 4d5b438のstart/pending failure、9432396の取消/OCE/cleanup置換。値/status/ownershipとcontextの証拠を混同しない。 |

この表は限定観測を原境界へ対応させる。古いpointerのreview-pending表示より、BOCCHI受入れと各publication receiptを優先する。異なる型shapeや未観測contextを同じ件数に足して証明したとはしない。

## 現行本体の接続

canonicalではCursor.Moveのasync境界内でDI factory、handler/source、Current、同期hookを順番に呼ぶ。各serviceは初回到達時に解決し、callbackを追加のasync helperへ移していない。Cursor.Dispose/Closeの通常async境界とfinallyでowned source/linkを終了する。consumer CurrentはMove内で保存した値を読む。

fusionではfacade MoveとRunSegmentのasync iteratorを使う。factory/handler/source/item処理は同じsegment内で順に観測され、yield/次Move/Disposeは各呼出callerのcontextに従う。canonical/fusionとも内部awaitはConfigureAwait(false)。これをExecutionContext flowの抑制や任意SynchronizationContext保持の約束と混同しない。

wrapperではWrapをそのまま呼び、typed upstreamと各segmentのMove境界を維持する。native async wrapperの境界は利用者のasync iteratorに属する。value/open requestの後続差分はgeneric宣言・request保持・null guardの条件であり、factory/hookを呼ぶMove/Disposeのasync本体には新しい隔離を加えていない。

対応済み形状について本体接続の不足は見つからず、この単位の製品C#差分は0である。unsupported receiver/session/async item hook等を文書だけで適合に変えない。user helper経由のambient書換えをSG/Analyzerが一般検出できるとは扱わない。

## 未確認の意味論と最小追加案

canonicalの既存pending sourceはValueTask gateの直接返却であり、user native async producer自身がAsyncLocal/cultureを書き換える確認とは区別する。cultureのfactory/getter/hook/downstream受渡しも製品Streamの既存観測で全面的に確認していない。新4代表を提案する。

- canonicalのnative async source producerが同期完了する場合。
- canonicalのMove/Dispose native producerが実pendingとなる場合。
- canonicalのnative Move失敗とnative Dispose失敗による自然な置換時。
- fusedのculture受渡しをnative実pendingで確認する場合。

sourceの同期forwarding methodから利用者のasync helperを呼び、そのhelperの通常C# boundaryを保存する。method entry/returnとhelper enter/resumeを別に記録する。pending ValueTask返却を確認してから完了通知でgateを解放し、単回消費を確認する。テストの制御delegateは既存probeのoptional fieldで、既存期待とreference bodyを変更しない。

factory H→handler、source Current→factory F1→F1、F1→factory Map→Map、Map→factory F2→F2、caller return/次Move/Dispose、native producerのresumeをAsyncLocalとcultureで記録する。consumer Currentを読んでもgetterを再実行しない。source helperはConfigureAwait(false)を選んだ利用者コードとして観測し、同期/pending SynchronizationContext・suppression・wrapperの既済み条件を再実行しない。

実行は未実施。4ケース/2consumer fixture/4reference比較を1 run、見込み240秒・上限600秒、await5秒とし、compile/生成/件数/trace/caller/native context/status/identity/単回消費/所有終了の差分で止める。public登録/ZEN0037、性能ゲートは維持する。

## 残要件と旧adapter

旧stage別async adapterの隔離を新oracleにしない。同期callbackの変更が後続へ見えることは新契約の差であり、隔離を消しただけで旧APIの性能改善とは呼ばない。D03の隔離比較案は別契約の意味論/局所cost資料として分離し、今回の製品性能値へ混ぜない。追加の速度/割当測定は行わない。

全context/async patternの列挙を完了条件にしない。一方、C07全体、async item hook C10、session C11、すべてのrequest/receiver/constraints/context/flow組合せ、alias/他provider、Analyzerの直接診断、public採用と性能は未完了として残す。現在の内部候補の一致だけで等価性不明なpublic経路を採用しない。
