# Generated Route services and Stream ownership

The public entry remains the generated `IZendiator` / `Zendiator`: callers send through `Send`, `SendAsync`, `SendAll`, `SendAllAsync`, and `StreamAsync`. No request-owned or Immediate-style dispatch API is introduced. Generated call-site interceptors are an implementation detail of those Mediator calls.

## Candidate correspondence

The second Fable answer contains seven candidate rows. S1 is the continuing synchronous-completion work; the other six rows are S1-stream, A, B, R3, X1, and X2. Its separate list of six unresolved questions is not the candidate list.

| Candidate | Implementation |
|---|---|
| S1: successful synchronous completion | A generated struct executes the synchronous prefix with the native builder `Start` boundary. Successful inner ValueTasks are consumed once inside that boundary; pending and unsuccessful operations use an async helper. Zero-stage and synchronous-Before-only Send routes use this path. Other callback/session shapes retain their existing orchestration. |
| S1-stream: synchronous MoveNext | Initialized cursor segments without sessions and with only synchronous item callbacks use the same prefix boundary around source MoveNext, GetResult, Current, and item callbacks. Pending, termination, and failures retain async cleanup. |
| A: Route-as-Service | Each generated dispatch route is an internal sealed Transient DI service. The Mediator retains its Route references, so the default Scoped Mediator reuses them within its scope. The Route owns orchestration and dependency slots, while the DI container owns user services. |
| B: scope-bound resolver | Closed dependency slots live on the Route. Open definitions use a per-Route map keyed by closed runtime type. Native DI performs the first resolution and its lifetime synchronization; Interlocked publishes the resulting reference. |
| R3: call-site static dispatch | A targeted syntax provider collects Mediator method invocations. Binding uses lightweight generated API declarations and produces an independent interceptor file per accepted location. A generated sealed receiver is called directly; other implementations of `IZendiator` receive the original interface call. |
| X1: handler-owned Stream | `ZendiatorHandler(OwnsStream = true)` lets a zero-stage, non-session Stream route return the handler's enumerable directly through `StreamAsync`. |
| X2: combined enumerable/cursor | Framework Stream segments use a cursor that also implements IAsyncEnumerable. An atomic claim lets the first acquisition return that object; later acquisitions create independent cursors. |

The literal eager constructor injection of all user stages from A is incompatible with B's stage-by-stage lazy resolution. The unified design adopts A's DI-owned Route and B's lazy slots. It does not add a resolution-mode switch or preserve an alternative eager graph. Constructing the Mediator resolves only internal Route skeletons and immutable lifetime policy, not user hooks or handlers. Direct construction therefore also requires a provider with the generated composition registered. The additional internal service descriptors and construction work are intentional architectural changes; their costs have not been measured.

Call-site dispatch accepts named reference-type receivers. Calls through type parameters or value types retain their original constrained dispatch, so a mutable struct implementation is not boxed into a different receiver. Generated signatures preserve assembly-specific extern alias paths, including generic arguments and constraints.

The canonical namespace reserves the generated `IZendiator` and `Zendiator` identities: configuration rejects existing source declarations, including partial declarations, before canonical emission. Extensions of these reserved types by another generator are outside this API ownership contract. The R3 API projection includes all public entries emitted for these types: selected Send routes, mixed Stream routes, and standalone public Stream routes. A mixed composition is accepted or rejected as a whole; its constructor cannot retain a rejected route. Legacy generation uses its separate API family, and a deliberate same-identity namespace collision already conflicts with its nonpartial interface and constructor.

## Lifetime and initialization contract

Register service overrides before `AddZendiator`. Registration captures a lifetime policy after generated default registrations have been added. Later replacement or removal of a hook, handler, or factory descriptor is outside this snapshot contract. Repeated configuration must not be used to mutate a composition's dependency lifetime after its first registration.

The last unkeyed descriptor at the snapshot boundary determines cache eligibility. Scoped and Singleton implementation types or instances may be retained. Transient and implementation-factory descriptors always go through the provider; the provider may itself retain a Scoped or Singleton factory result. Keyed descriptors do not replace unkeyed policy.

A Mediator service registered before `AddZendiator` is preserved by TryAdd. Its retained Transient Routes are owned by that Mediator's resolving provider: a Singleton Mediator holds root-owned Routes, while a Scoped Mediator holds scope-owned Routes. User dependencies remain lazy. Resolving a Scoped user dependency through a Singleton Mediator therefore fails at that dispatch stage under ValidateScopes, rather than failing while the Mediator constructor resolves an internal Scoped Route.

Initialization does not introduce a lock around callbacks or a second lock around DI factories. Competing first callers resolve through native DI, then publish with Interlocked. Failed or null resolutions do not populate a slot, so provider retry behavior remains available. Boxed value-type services remain the provider's original box. Slots and generic maps belong to a Route instance, so mutable cached service state is not shared between containers or scopes by generated static fields.

The Route's Dispose marks it as disposed and never disposes borrowed dependencies. The container disposes its services. Each cached hit also calls the original provider for `IServiceProvider`, so its disposal check remains authoritative even while a later asynchronous disposable is still blocking scope cleanup. This applies to closed slots, open generic maps, and a later lazy stage of an already pending operation. Microsoft DI rejects these lookups from the beginning of scope disposal; a custom provider controls when its own GetService rejects disposal. A cache hit therefore still performs this provider probe, rather than promising zero DI calls. This does not add ownership of the caller's scope or serialize operations with scope disposal; a lookup accepted just before disposal can race with later use just as a native lookup can.

## Completion and context

Argument guards remain at the public dispatch boundary. Execution failures still pass through a ValueTask builder, including OCE from an uncanceled foreign token or an already Faulted ValueTask. A simple `FromException` tail return would change Canceled/Faulted normalization and is not used as the Send failure result.

The successful Send fast path consumes the inner operation before returning an immediate ValueTask. It does not return an unconsumed pooled source to the caller or consume a source twice. Pending helpers are started while the synchronous prefix's context is still active. This preserves the consumption point and captured execution context.

The prefix uses the public `AsyncValueTaskMethodBuilder.Start` API rather than removing the native ExecutionContext boundary. In the .NET implementation, Start saves and restores ExecutionContext and SynchronizationContext around MoveNext. This also covers suppressed flow, for which `ExecutionContext.Capture()` can return null. See the [runtime Start implementation](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Private.CoreLib/src/System/Runtime/CompilerServices/AsyncMethodBuilderCore.cs) and [public builder forwarding implementation](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Private.CoreLib/src/System/Runtime/CompilerServices/AsyncValueTaskMethodBuilderT.cs).

Framework Stream cursors retain the busy CAS, release with Volatile, lazy stage guards, Current cache, single consumption, and cleanup priority. A false filter retries through a fresh source cancellation guard. Opaque wrappers keep their own control and token boundaries.

## Handler-owned Stream contract

The explicit capability is a different Stream execution contract. `StreamAsync` checks its request, resolves the handler, calls HandleAsync, checks its nonnull return, and returns that enumerable. Handler construction and synchronous HandleAsync failures can therefore occur at StreamAsync, rather than at the first MoveNext. The framework's cursor schedule does not describe this path.

The handler and its enumerable own API/enumeration token composition, cancellation observation points, independent enumeration, Current behavior, overlapping-operation behavior, and cursor cleanup. They may use native async-iterator semantics; the framework does not add its Current/operation guards or diagnostic messages. The DI-owned handler itself remains borrowed. A pipeline containing a stage, wrapper, or session retains framework orchestration even when the handler declares OwnsStream.

Declaring the capability is not a proof about an arbitrary forwarding handler or compiler iterator. In particular, verify independent token composition when two cursors are acquired before either starts and one is canceled or disposed first. An explicit enumerable factory can create a fresh iterator for each acquisition and compose that cursor's tokens independently. The capability fixture exercises this pattern; its earlier raw-iterator variant failed that cancellation scenario and is retained as verification evidence.

## Enumeration identity

For a framework-owned enumerable, the first acquired cursor is now the enumerable object itself. This object identity is an intentional compatibility change. Its enumeration token is assigned only to that claimed cursor. Every later acquisition, including one before the first cursor has moved, receives distinct state and its own enumeration token. Acquiring a cursor does not resolve user services or start the source. Separate wrapper Open calls still create independent enumerable state.

## Verification and measurement order

Functional checks cover the changed binding, context, consumption, lifetime, cancellation, and ownership behavior. Generated sources are retained for review. All candidate changes are reviewed together with Copilot CLI `claude-fable-5.1`; important findings are resolved before measurement. The parent reviews the real diff and finding-resolution record before a performance run begins. No speed or allocation improvement is asserted from the implementation alone.
