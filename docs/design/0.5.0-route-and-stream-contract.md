# Generated Route services and Stream ownership

The public entry remains the generated `IZendiator` / `Zendiator`: callers send through `Send`, `SendAsync`, `SendAll`, `SendAllAsync`, and `StreamAsync`. No request-owned or Immediate-style dispatch API is introduced. Generated call-site interceptors are an implementation detail of those Mediator calls.

## Generated execution

| Path | Implementation |
|---|---|
| Plain SendAsync | Zero-stage and synchronous-Before-only routes without factories or After/Exception/Finally callbacks return the handler's original ValueTask from an ordinary method. Routes with other callbacks, wrappers, or sessions retain their orchestration. |
| Shared dependencies | Route bodies and dependency slots live directly in the partial Mediator. Closed reference dependencies use typed fields and accessors; value-type receivers retain the provider's original object box. Open definitions share a lazy map keyed by closed runtime type. No resolver object or lifetime policy is constructed. |
| Call-site static dispatch | A targeted syntax provider binds Mediator calls and emits an independent interceptor per accepted location. A generated sealed receiver is called directly; other implementations of `IZendiator` receive the original interface call. |
| Handler-owned Stream | An eligible zero-stage, non-session Stream route returns the handler's enumerable directly by default. `ZendiatorHandler(OwnsStream = false)` selects the guarded framework cursor for that zero-stage route. |
| Fused item Stream | An accepted single borrowed segment with class Handler/Hook receivers and Filter/Map callbacks uses one generated C# async iterator. A thin enumerable creates a fresh iterator for every acquisition. Factories, sessions, wrappers and upstream segments are excluded. |
| Nonfused framework Stream | Other accepted cursor segments keep their existing synchronous MoveNext prefix boundaries, guards and cleanup. The first acquisition claims the enumerable/cursor object; later acquisitions create independent cursors. |

Construction stores the exact provider passed to the Mediator without resolving user stages. Dependencies remain lazy and are captured when a stage is first reached. Direct construction does not require a generated policy registration; a missing dependency fails at the stage that needs it. The Mediator explicitly implements `IServiceProvider` so internal helpers share its captured dependencies. This does not introduce a separate dispatch entrance.

Call-site dispatch accepts named reference-type receivers. Calls through type parameters or value types retain their original constrained dispatch, so a mutable struct implementation is not boxed into a different receiver. Generated signatures preserve assembly-specific extern alias paths, including generic arguments and constraints.

The canonical namespace reserves the generated `IZendiator` and `Zendiator` identities: configuration rejects existing source declarations, including partial declarations, before canonical emission. Extensions of these reserved types by another generator are outside this API ownership contract. The R3 API projection includes all public entries emitted for these types: selected Send routes, mixed Stream routes, and standalone public Stream routes. A mixed composition is accepted or rejected as a whole; its constructor cannot retain a rejected route. Legacy generation uses its separate API family, and a deliberate same-identity namespace collision already conflicts with its nonpartial interface and constructor.

## Lifetime and initialization contract

Generated registration uses one Scoped descriptor, `IZendiator -> Zendiator`, and Transient defaults for user handlers, hooks, and session factories. There is no concrete Mediator descriptor or interface alias factory. Register overrides before `AddZendiator`; TryAdd preserves them. An entry lifetime override must target `IZendiator`. Registering only the concrete type no longer changes the interface entry. Composition fingerprint validation remains in place.

Each Mediator captures the first published successful native result for every dependency type, including Transient and implementation-factory registrations. Subsequent stages and routes reuse that object. Closed reference dependencies use `T?` storage and `T`/`T?` accessors; the native object-to-T cast occurs on cold resolution. Value-type handlers, hooks and factories keep object storage and object-returning resolution so calls through their contract interfaces preserve the provider's original box. Open generic dependencies share a closed-type key within that Mediator. A directly resolved Transient or another manually constructed Mediator may obtain a different object. A captured session factory is reused, while its session creation and owned/borrowed cleanup still occur per operation.

Native DI owns activation, Scoped synchronization, and disposal. The generated cache adds no lock around constructors or factories. Competing first callers may activate several Transients; callers whose own resolution succeeds with a nonnull value use the same cold CompareExchange publication winner. This also preserves a winner published by a reentrant dispatch. Losing objects remain DI-owned and are never disposed by the Mediator. A native resolution failure still propagates its original exception even if another caller publishes a winner; a null result produces the Required accessor's missing-service error. Neither failure is captured. A later call reads an existing winner or retries resolution. Closed-slot warm hits use Volatile.Read, with zero generated publication CAS operations and no native liveness probe.

Slots and maps belong to the Mediator instance, with no cross-provider static state. A Singleton entry retains its root provider; resolving an overridden Scoped dependency therefore fails lazily at the dispatch stage under ValidateScopes. A Scoped entry retains its scope provider. A forwarding custom provider remains the authority for each first successful activation; cache hits do not call it again.

The Mediator does not own its provider or borrowed dependencies and does not register for disposal tracking. Keep the caller's scope alive until all sends and enumeration have completed. Using a captured Mediator after scope disposal, or disposing its scope while an operation is pending and then resuming it, is unsupported. Removal of the hit probe intentionally removes the previous generated rejection guarantee; it does not guarantee successful use after disposal.

## Completion and context

Public entry argument guards remain. Plain SendAsync checks cancellation and runs dependency resolution, synchronous Before callbacks, and the handler call directly. A synchronous failure, including cancellation, throws synchronously. Synchronous prefix changes to AsyncLocal, CultureInfo, or SynchronizationContext are visible to the caller. This is an intentional change from the former builder Start boundary.

Plain SendAsync returns the original ValueTask without checking completion, consuming GetResult, or repackaging it. The caller must consume it exactly once, including an already completed pooled source. Its original Faulted/Canceled status is preserved: an already Faulted operation containing OperationCanceledException is not normalized to Canceled by the framework. Pending consumption runs under the caller's usual await/context behavior.

Send routes requiring asynchronous Before, After, Exception, Finally, wrappers, or sessions retain their existing completion and context boundaries. Nonfused framework Stream synchronous segments also retain their builder Start boundary around source MoveNext, GetResult, Current, and item callbacks, including suppressed-flow behavior. Native builder Start saves and restores ExecutionContext and SynchronizationContext; see the [runtime implementation](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Private.CoreLib/src/System/Runtime/CompilerServices/AsyncMethodBuilderCore.cs).

Nonfused framework Stream cursors retain the busy CAS, release with Volatile, lazy stage guards, Current cache, single consumption, and cleanup priority. Opaque wrappers keep their own control and token boundaries. The fused item path below uses native C# iterator completion and context behavior instead of an additional handwritten cursor boundary.

## Fused item Stream contract

Fusion applies only to an already accepted route with class Handler and Hook receivers, one borrowed consumer segment, and synchronous or ValueTask Filter/Map callbacks. It excludes Handler/Hook factories, sessions, opaque wrappers and upstream segments. Supported closed/open generics, type-changing maps and value requests retain their existing acceptance rules; this backend does not admit new route shapes. Wrappers can replace requests/tokens, cache, retry or open upstream several times, while sessions have per-operation acquisition and cleanup ownership. Their existing segmented execution remains separate.

`StreamAsync` returns a thin Sequence. Every `GetAsyncEnumerator` creates a fresh `RunSegment(api).GetAsyncEnumerator(enumeration)`, keeping two acquired cursors and their linked-token ownership independent. API/enumeration token composition can now allocate a linked CancellationTokenSource at enumerator acquisition, rather than at the first MoveNext. User DI resolution and handler execution still wait until the first MoveNext. Disposing one enumeration must not detach another's cancellation.

Each iteration checks cancellation before source MoveNext and before every reached Hook. A false Filter returns to the source guard. After a successful source move, Current is read once, before the Hook guards; later stages resolve lazily. Typed item locals preserve type-changing maps without object item transport. Source, callback and Dispose ValueTasks are each consumed once. A try/finally disposes the source once on completion, failure or early disposal; cleanup failure takes priority over a Current/callback failure. Borrowed Handler/Hook services remain DI-owned.

Current follows the generated C# iterator contract: read it only after a successful MoveNext and before the next move or disposal. MoveNext/Dispose operations must be sequential and awaited once. The former custom exceptions for unavailable Current or overlapping operations are not guaranteed on this path. Its handwritten busy CAS, outer StartMove/FinishMove boundary and duplicate Current cache are removed; the compiler's iterator state, Current storage and native async/context boundaries remain. This is an intentional execution-contract change. `OwnsStream = false` controls zero-stage handler ownership, not selection of the guarded cursor for these staged routes.

## Handler-owned Stream contract

Handler ownership is the default for eligible zero-stage routes. `StreamAsync` checks its request, resolves the handler, calls HandleAsync, checks its nonnull return, and returns that enumerable. Handler construction and synchronous HandleAsync failures can therefore occur at StreamAsync, rather than at the first MoveNext. An explicit `OwnsStream = false` restores the framework-managed cursor and its lazy initialization schedule.

The handler and its enumerable own API/enumeration token composition, cancellation observation points, independent enumeration, Current behavior, overlapping-operation behavior, and cursor cleanup. They may use native async-iterator semantics; the framework does not add its Current/operation guards or diagnostic messages. The DI-owned handler itself remains borrowed and follows the Mediator capture contract. Staged routes use their selected generated backend regardless of OwnsStream; wrappers and sessions retain their existing orchestration.

Handler ownership does not prove an arbitrary forwarding handler or compiler iterator composes tokens independently. If two cursors are acquired before either starts, cancellation or disposal of one must not accidentally affect the other. An enumerable factory can create a fresh iterator and compose tokens for each acquisition; the handler-owned fixture exercises this pattern. Choose explicit false when the framework's token composition and cursor guards are required.

## Enumeration identity

A fused item Sequence is separate from every acquired iterator. Nonfused framework enumerables retain first-acquisition self-reuse: the first cursor is the enumerable object, and later acquisitions, including one before the first cursor moves, receive distinct state and their own token. Neither generated path resolves user services or starts the source merely by acquiring a cursor. Separate wrapper Open calls still create independent enumerable state.

## Generation pipeline boundaries

Composition output uses registrar, dependency, namespace and extern-alias metadata captured during the route's initial parse. It is rendered directly instead of joining/reparsing family output or rendering/renaming all Multi routes and discarding most of that text. Registration call-site location is captured during the existing semantic binding and reused by eight registration output paths, replacing eight separate CompilationProvider joins/rebindings with one shared capture. Current diagnostic locations remain separate from structurally compared route values.

Legacy GenerationModel now feeds SourceEmitter directly. The unused conversion to a nonexecuting legacy Fusion IR and its discarded lowering checks have been removed. The full legacy renderer remains separate because it still implements runtime-type Notification dispatch, open notifications and zero/multiple subscribers, partial-class generation in arbitrary namespaces, and opaque continuation behaviors that the canonical backend does not implement. Routing both models through another adapter would not remove that work or justify dropping those features.

Initial route parsing, necessary private-name/type rewrites and the lightweight API projection parse for correct overload binding remain. Renderer unification and parse elimination are not complete. These changes preserve Mediator entry, attribute-based discovery and split outputs; their build-time benefit has not been measured.

## Verification and measurement order

Targeted functional checks cover binding, consumption, lifetime, cancellation and ownership; generated sources are retained for review. Final review of the current P3/P5/P6 changes, the full PR and their integration remains pending, as do performance measurements. Important findings and the exact diff are reviewed before a performance run. No runtime, allocation or generation-speed improvement is asserted from source changes alone.
