## 結論

独立した手書き実証の semantic gate は成功したが、今回の allocation 診断では既存の生成 pooled 版より B/op が多かった。時間は未測定で、状態保持方式の改善も製品への採用も成立していない。既存 `[GeneratePooledProducer]` の動作を変更していない。

通常版、実際に interceptor/helper が生成された pooled 版、公開 AsyncIteratorMethodBuilder を使う手書き実証を、同じ WorkStreamCursor 本体の処理と共通 consumer で比較した。Task.Yield、token check、probe、cleanup、値は削除していない。raw producer と生成 Mediator 経由を別系列にした。

## 契約の検証

item completion と列挙全体の終了を分離し、各 item の成功時に builder.Complete を呼ばない。completion cell の再利用には consumer の消費と producer 側の完了処理の両方を必要とする。通知前に owner の世代 field を解放し、inline consumer が次の Move へ再入しても、旧 producer が新世代を後から書き換えない。

通常/pooled/retained × raw/Mediator に対し、同期/非同期、0/1/16 items、full/early、例外、cancel、独立列挙、cold Dispose、保持された世代、再入を検証した。Move ごとに AsyncLocal と culture を変える controlled queue の context gate も成功した。ただし controlled inline dispatch の結果をすべての scheduler の保証とはせず、Mediator 側の ExecutionContext 処理と producer 単体の挙動を区別する。

SDK 10.0.403 / .NET 10.0.14 で locked restore、Release の非 incremental 再compile、semantic、限定 format が成功し、警告・エラーは 0。初回に cwd の指定誤りで SDK 11 preview が選択された際の出力は保存したが、採用する検証証跡から除外した。実 compiled IL で pooled interceptor→生成 helper→PoolingAsyncValueTaskMethodBuilder への呼び出し経路と、通常版の元 helper 呼び出しを確認した。

## Allocation 診断

全 12 ケースの total pass が終わるまで fixture EventListener を作らず、その後に型 sampling を別 pass で実行した。total は process-wide の GC.GetTotalAllocatedBytes(precise: true) で、runtime のバックグラウンド処理も含む。20,000 operations（16 items）または 2,000 operations（1,024 items）、warmup は各 512 operations。正式な BDN 時間・順位の結果ではない。

型 sampling では、通常版の項目ごとの state-machine box、retained の cursor/ItemCompletion/列挙用 box などを観測した。pooled の sample が少ないケースや、Mediator の両最適化系列で観測した queue callback から、厳密な型別 bytes や allocation 移転の不存在は証明できない。tracing が Yield の経路を変える可能性があり、sample 比率を total pass の B/op に掛けない。

実際に読み込まれた .NET 10.0.14 CoreLib の IL から、AsyncIterator builder、box-aware dispatcher、Yield の実装、内部 ThreadPool queue まで 6 つの参照辺を確認した。これは利用可能な参照経路の証明であり、その実行分岐や native code、cached Action の別型への allocation 移転がないことの証明ではない。
