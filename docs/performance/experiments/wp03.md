## Send5.Typed の上位 caller の診断

controls の結果を受け、正式に保存した BDN bundle と同じ bytes を別の非 timing process で Tier1 診断した。SDK 10.0.403 / runtime 10.0.14 で probe もビルドした。元の timed child の native code を遡って取得したものではなく、PGO 履歴と code layout が当時と同一とは主張しない。新しい時間集計、製品変更、属性追加は行っていない。

Send5 の生成 route は同期 Before 5 段と handler を並べた SendAsync で、この経路には ExecuteRegion / MoveNext はない。standalone Typed は両者とも cache hit を inline 化し、cold 部分の outline 化で 1,976 → 1,458 bytes になった。これだけでは大きな時間差を説明できない。

上位の保存 BDN workload lambda の Tier1 では、同期成功 path に次の差があった。

- baseline と候補の両方に Work.Enter の 5 call が残る。workload 自体は減らしていない。
- baseline の handler Service getter、Work.Handle、ValueTask<int> constructor、AwaitHelper.GetResult の 4 call は候補で消える。
- 候補には置換先の ValueTask<int>.get_Result の 1 call が残る。成功 path 全体は 9 → 6 call になった。

cold 分離で上位 caller に inline 化の余地が増えたという説明は、正式 3 ペアの改善と整合する。ただし compiler の inline 拒否理由や cycle 寄与は取得しておらず、約 47% の因果寄与を定量的に証明してはいない。code bytes の比を速度比へ換算せず、ScopeK1 の保護未達を覆す材料にも使わない。
