# WP02: cursor の稀な状態の分離

## 結論

## 変更と守った契約

`_disposeError`、`_disposeCompletion`、`_pendingMove` の 3 参照を `_rare` の 1 参照へ置き換え、必要な場合だけ `RareState` を確保する。CAS で公開した helper を owner 単位で再利用し、move ごとには作成しない。同期成功と同期 cleanup のためだけには helper を作らない。

pending move の公開、busy の解放、cleanup 完了の公開、dispose completion の共有は従来の順序を維持した。同時 dispose と move が別の helper を採用しないようにし、例外と completion は同じ CAS winner から参照する。token、MoveCompletion、ValueTask の消費・再利用条件、公開 API は変更していない。

64-bit の参照差は owner 当たり 16 B と見積もれるが、class layout と alignment は実測前の仮定である。非同期・例外・pending dispose では helper の header と field が追加される。その追加費用を同期経路の利益で隠さず、各ケースの B/op として記録する。

## 既存 completion との同居案

既存 `MoveCompletion` に field を追加するだけなら protected API や sealed を変えずに済むが、複数の cache cell と overflow cell のすべてを大型化する。owner の状態を一つの cell に固定する場合は、世代をまたぐ保持と外部派生 cursor の再利用を別に設計する必要がある。

Task-backed fallback と dispose-only には `MoveCompletion` がないため、同居だけでは全経路を扱えず、別 helper と型判定が残る。runner は close 時に切り離されるため、そこに同居させると cache cell などの保持期間が変わる。`DisposeCompletion` への集約には、pending move のためだけに不要な TaskCompletionSource と Task を作らない設計が必要になる。

このため、最初の比較では 1 個の遅延 helper に限定した。独立レビューでも、変更範囲を小さく保つ判断は妥当とされた。非同期側の追加費用が採用条件を満たさない場合は、pending field を owner に残して dispose 関連の 2 参照だけを分離する案を、別の単独試作として検討する。

## 正式比較の結果

2026-11-07 14:53:24–15:23:28 UTC、baseline/candidate、candidate/baseline、baseline/candidate の順で実行した。10 ケース × 2 variant × 3 ペアの全 60 ケースが成功し、validation error は 0 件。各 variant の source、生成物、runtime・generator・benchmark assembly は各 run の session と actual-child artifact gate に拘束した。
