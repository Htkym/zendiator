# WP05: 新規 scope の allocation 費用分解

この文書は先行allocation診断の記録である。続く実装・正式48セルの測定結果と採用判断は[明示的eager依存注入](wp05-eager.md)に記載した。以下の「未検証」「新しいAPIは作っていない」は、この先行診断時点の記録として残す。

## 結論

既存の LazyBlocks 設定で、同じ App の同期 ScopeK1 allocation が Send0/5 とも 56 B/op 減った。新しい eager API は作っていない。prefetch は初回 Send の allocation を依存取得へ移すだけで、scope 全体の総量を減らさなかった。時間の改善と eager DI の採用条件は未検証である。

Baseline は `7c69f2a7408a68f36cf25abc3c6ac74ef00c5054`。SDK 10.0.403 / .NET 10.0.14、native DI 10.0.12。同じ App の属性へ `ClosedServiceCache = ClosedServiceCacheMode.LazyBlocks` を加えた一設定だけを別 stage で比較した。既定値・既存の benchmark・製品 source は変更していない。

## 同一 operation の境界

1-op smoke と 4,096-op の各 operation では、scope 作成、初回 Mediator resolve、初回 Send、Dispose の順に連続した allocation counter の差を取る。すべての Send の同期成功と値 42 を確認した。独立した時間の平均値を引き算した結果ではない。

| 設定・経路 | Scope | 初回 Mediator resolve | 初回 Send | Dispose | 全体 |
| --- | --- | --- | --- | --- | --- |
| Inline Send0 | 128 | 432 | 24 | 0 | 584 B/op |
| Inline Send5 | 128 | 432 | 144 | 0 | 704 B/op |
| LazyBlocks Send0 | 128 | 232 | 168 | 0 | 528 B/op |
| LazyBlocks Send5 | 128 | 232 | 288 | 0 | 648 B/op |

smoke と 4,096-op の値は一致し、境界和と全体も一致した。constructor control は Inline 248 B、LazyBlocks 48 B、取得済み Mediator の cached Send は両設定とも 0 B。constructor control は別の control であり、上の表には二重に加算していない。

closed cache は 27 slots で、Send0 は 1、Send5 は 6 を使用する。Inline は未使用 slots も Mediator に持つ。LazyBlocks は 16+11 slots の 2 blocks で、今回確保したのは 144 B の先頭 block だけだった。constructor の −200 B と初回 block の +144 B が、全体の −56 B と整合する。

明示的な依存 prefetch では、Inline の 24/144 B、LazyBlocks の 168/288 B が依存取得の境界へ移り、Send は 0 B、scope 全体は不変だった。これは constructor injection 自体を測った結果ではなく、activation を早めるだけでは allocation 削減にならないという限定的な確認である。

## 証跡と制限

locked restore、Release build、1-op、4,096-op、別 pass の 131,072-op 型 sampling が両 stage で成功した。修正後の build は警告・エラー 0。既存 lock は不変。初回の診断 project の alias 衝突による compile failure の記録は保存し、製品変更とは区別した。

GCAllocationTick は Inline で 724/872、LazyBlocks で 655/802 samples。Mediator、DI scope/cache、依存、LazyBlocks の ServiceBlock_0 を観測した。型の sample 数から厳密な型別 B/op を計算していない。sampling と listener の費用は上の同期 counter 境界と混ぜていない。

この診断は逐次実行で、同時初回取得・CAS競合・disposal sentinel を検証していない。native DI の破棄所有権を変える実装は追加していないが、この診断だけで全所有権契約を証明できたとはみなさない。初回 WP00 の ScopeK1 時間を新しい実測値として再利用せず、16,384 precreated scopes を使う FirstSend の時間と、通常 ScopeK1 の時間を加減算しない。

[結果 JSON](wp05-allocation-summary.json)と source/generated/DLL pins、生ログは `D:\gitroot\zendiator-wp05-evidence-20261107` に保存した。独立 fixture は `D:\gitroot\zendiator-wp05-profile-20261107` と `D:\gitroot\zendiator-wp05-lazyblocks-20261107`。新 eager mode の意味・対象 route・例外/再入/override と時間効果は今後別途判断する事項であり、今回の 56 B を新機能の成果として扱わない。
