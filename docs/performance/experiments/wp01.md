# WP01 実験結果

## 結論

現行の代表条件では棄却する。Stream5 の sync early break では、生成コードの interface 呼び出しが warm Tier1 の native code で既に最適化されていた。L7 の 0 段には対象の middleware 呼び出しがない。直接呼び出しを追加する製品コードは作成していない。

これは速度比較の結果ではない。今回の棄却は計画の着手条件と、JIT が既に同じ呼び出しに最適化している場合の棄却条件に基づく。別の runtime、AOT、別の middleware 形状まで同じ結果とは主張しない。

## 比較対象

- Baseline SHA: `7c69f2a7408a68f36cf25abc3c6ac74ef00c5054`
- Candidate SHA: なし。
- 対象: `ZendiatorStream5.EarlyBreak`、Count=16、Asynchronous=false、既定の standard enumeration。
- SDK / runtime / DI: 10.0.403 / .NET 10.0.14 / DI 10.0.12。
- 既存 fixture を 250,000 回ずつ 4 round 呼び、各 round 後に 100 ms 待機した。時間の集計と順位判定は行っていない。
- 診断設定: `DOTNET_JitDisasm=*9AA217*:*`、出力先は `.local/perf-plan/wp00/jit-probe/baseline-stream5-jit.txt`。tiering・PGO は既定のまま。
- 抽出結果: `.local/perf-plan/wp00/jit-probe/baseline-stream5-open-calls.json`。

## 観測

生成コードには、具体的な sealed `ZSBehavior1〜5` を `IStreamMiddleware` に cast して `OpenAsync` を呼ぶ箇所がある。

Tier0 と Instrumented Tier0 では、5 段すべての開始 state machine に `call [r11] Zendiator.IStreamMiddleware.OpenAsync` が残っていた。warm Tier1 の同じ 5 メソッドでは、この interface 呼び出しは残らず、middleware 本体が inline 化され、対応する具体的な `Upstream1〜5.OpenAsync` 呼び出しになっていた。raw source 側の Cursor0 も併せて抽出した。

Tier0 だけを根拠に間接呼び出しが残ると判断せず、Tier1 を確認した。warm な代表比較のために generator の分岐を増やす根拠は得られなかった。

## 正当性と不確実性

製品コード、公開 API、binding、fallback は変更していない。明示的 interface 実装や non-sealed 派生再実装には、従来の経路がそのまま残る。

正式な時間・B/op 比較は行っていない。warm Tier1 の dispatch 除去を確認したことは、cold startup の全費用が消えたことや、別の最適化余地がないことを意味しない。
