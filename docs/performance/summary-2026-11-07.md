## 採用しなかった理由と証拠の限界

WP03 は Short +9.071%、H FirstSend +3.294%、ScopeSend0 +5.789% の 3 件で固定 3% の保護条件を満たさなかった。TypedSend5 の約 47.17% 改善とは相殺しない。測定のばらつき・drift を含むため、保護失敗の原因を製品コードと断定していない。

WP04 は独立した 120 raw / 60 pair の統計・GC・証跡照合に合格し、5 段の約 200 B/op 削減を再現した。一方、feature 系列の時間改善成立は 0 件。中央値による 3% 回帰判定と全 3 回遅化はともに 0 件でも、単 round の +43.23%（feature）・+45.63%（既定保護）、比較右側の round 間 drift 59.96%・45.42% が未説明であり、時間保護を確認できず非統合とした。WP04 の full 3,622 件は製品 stage 時点のものであり、その後の限定 30 件とは区別し、全候補の最終状態で full を再実行したとは扱わない。

WP05/06 は allocation 診断であり、正式な時間・順位の結果ではない。WP06 の process-wide total と別 pass の型 sampling は混合せず、元 baseline の約 115 kB から proof の値を直接差し引かない。既存の work・probe・Task.Yield・token・cleanup、Mediator API、DI 所有権、Stream 契約を保ち、既存機能と新しい改善を区別した。

受領計画は全 WP の実装・採用を完了条件としていない。WP07 は二重 completion、WP09 は最終 throw/builder 例外完了の主要因 profile がそれぞれ未成立であり、WP08 は元 SendAsync fixture 確認後も残存費用が未特定のため非着手。WP10 は P3 の別系列として未実施で、.NET 10 の改修効果へ算入しない。各対象の結果・改善未証明理由、契約、opt-in/default の区別、再現証跡を成果物として残す。

製品 main は変更せず、main への push・merge・release は行っていない。Fast Mode を使用しない条件を維持した。
