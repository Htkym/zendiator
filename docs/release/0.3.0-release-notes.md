# Zendiator 0.3.0

[日本語](0.3.0-release-notes.ja.md)

Zendiator 0.3.0 changes dependency registration and the generated mediator's disposal contract. The usual `AddZendiator()` registration, default Scoped mediator, and common `IZendiator.SendAsync` entry remain available. Review the changes below when upgrading from 0.2.0.

## Dependency lifetime

With the default Scoped mediator, generated handlers and Behaviors now register as Transient. In 0.2.0, they inherited the mediator's Scoped lifetime. Zendiator still captures the first resolved instance of each service type per mediator, including Transient services. The change affects sharing with other consumers in the same scope and when a distinct mediator instance is created; it does not cause a new handler to be resolved on every send through the same mediator.

If the application requires the previous sharing behavior, set `configuration.DependencyLifetime = ServiceLifetime.Scoped`, or register the affected services as Scoped before calling `AddZendiator()`. Check constructor counts, retained state, concurrency, and disposal ownership when upgrading. The configuration overload also accepts separate mediator and dependency lifetimes. DI remains responsible for construction and disposal.

## Mediator disposal and migration

Generated mediators no longer implement `IDisposable`. Dispose the DI scope after sends and stream enumeration finish. Sending through a retained mediator after its scope or root provider is disposed is unsupported; the previous guarantee of an `ObjectDisposedException` is gone. The `ZendiatorRootLifetime` type and constructor overloads that accepted it were removed. Code that directly calls `ZendiatorServiceResolver.Dispose()` must change.

The generator package includes ZEN0021–ZEN0023 warnings for directly provable lifetime mistakes: treating a generated mediator as `IDisposable`, returning it from a local `using` scope, and sending after explicit scope disposal in the same method. These warnings do not establish safety for complex asynchronous work or mediators stored in fields. Keep the scope alive until dispatch completes. See the [migration guide](../migrating-from-mediatr.md) and [dispatch lifetime contract](../optimized-dispatch.md).

The exact base type of some generated mediators also changes to a composition-specific or single-service resolver. Ordinary `AddZendiator()` and `IZendiator.SendAsync` calls do not need to change. Code that inspects the generated class's base type must be updated, and consuming projects must rebuild with the matching generator and runtime packages.

## Performance and limits

Composition-specific service slots avoid sparse cache pages when unrelated mediator compositions have already used many service types. A single-service resolver covers eligible routes. These changes do not establish a general speed ranking. Warm sends can retain 0 B additional allocation under the documented synchronously completing, allocation-free handler and Behavior conditions; first DI resolution and asynchronous suspension are separate costs. The [use-case benchmark](../../benchmarks/README.md) provides reproducible Send, Notification, and Stream comparisons. Its one-launch results do not prove an overall fastest library.

The [known limitations](known-limitations.md) remain, including the Native AOT restriction for open-generic DI handlers closed over value types. Native AOT verification targets win-x64.

## Install or upgrade

```shell
dotnet add package Zendiator --version 0.3.0
```

`Zendiator` includes the generator and depends on `Zendiator.Abstractions`. Update explicit references to both packages to 0.3.0, then rebuild consumers to regenerate dispatch code. The default registration remains:

```csharp
using Zendiator.DependencyInjection;

services.AddZendiator();
```

See the [README](../../README.md) for examples and supported operations.
