# Release notes: Zendiator 0.2.0

[日本語](0.2.0-release-notes.ja.md)

Zendiator 0.2.0 unifies dispatch around lazy dependency capture with standard DI,
improves incremental source generation, and documents the current design. This is a
pre-V1 release with a breaking lifetime change; review the upgrade notes below.

## Breaking change: dependency reuse

Each mediator retains the first resolved handler or behavior instance for each service
type. This includes Transient registrations: subsequent sends and retries through the
same mediator reuse an already captured instance rather than resolving a fresh one.

DI remains responsible for construction and disposal. Scoped and Singleton sharing
follows the container's registrations. Short-circuited pipelines do not construct
downstream dependencies that have not been reached. The mediator remains Scoped by
default, while generated handlers and behaviors now register as Transient. To keep
sharing them with other consumers in the scope, set
`configuration.DependencyLifetime = ServiceLifetime.Scoped` or pre-register the
affected services as Scoped before `AddZendiator()`.

When upgrading, check constructor counts, state retained between calls, concurrency,
and disposal ownership. Keep the scope alive until sends and stream enumeration finish.
Lazy dependencies may not be validated until first dispatch even with `ValidateOnBuild`.
See [dispatch lifetime](../optimized-dispatch.md) for the complete contract.

The generated mediator no longer implements `IDisposable`; DI still disposes its
handlers and behaviors. Dispose the scope rather than the mediator. Calls on a
cached mediator after scope or root-provider disposal are unsupported and no
longer guaranteed to throw `ObjectDisposedException`. The constructor overloads
accepting `ZendiatorRootLifetime` and that root marker type were removed.
The generator package includes analyzer warnings ZEN0021–ZEN0023 for directly
provable lifetime misuse. See the [migration guide](../migrating-from-mediatr.md)
for their coverage and limits.

## Construction

The standard entry point needs only one registration call:

```csharp
using Zendiator.DependencyInjection;

services.AddZendiator();
```

Use the normal `BuildServiceProvider()` or host builder. No custom provider, factory,
mode selection, or additional initialization is required. Use a configuration lambda
only to specify assemblies, behaviors, a namespace, or other settings. Application
registration wrappers are optional, not an extra setup requirement.

## Implementation and documentation

- Use a single lazy-capture dispatch path with generic struct continuations.
- Separate generated stream startup from steady-state `MoveNextAsync` processing.
- Reuse interface discovery and type-name results within each generator analysis.
- Project Roslyn analysis into immutable, structurally comparable emission models.
  Equal models skip template expansion; interceptor location changes are handled separately.
- Organize source by responsibility and use raw string templates with meaningful
  emission models instead of long, unrelated argument lists.
- Update the English and Japanese READMEs and MediatR migration guides. Add the
  [Constitution](../../Constitution.md) as a public architecture and maintenance reference.

Compilation changes still rerun semantic analysis. This release does not claim
per-type incremental analysis or that unrelated edits require no generator work.

## Installation and upgrade

```shell
dotnet add package Zendiator --version 0.2.0
```

`Zendiator` includes the generator and depends on `Zendiator.Abstractions`. Contracts-only
projects can reference `Zendiator.Abstractions` alone. Update explicit references to both
packages together. Rebuild consuming projects to regenerate their dispatch code.

See the [README](../../README.md), [MediatR migration guide](../migrating-from-mediatr.md),
and [known limitations](known-limitations.md). Native AOT verification targets win-x64;
open-generic DI handlers closed over value types remain outside the tested supported path.

## Verification and performance scope

The release gates are Release build and tests, formatting, package contents, samples,
isolated PackageReference consumers, and the win-x64 Native AOT matrix. Local preparation
does not replace verification of the final tag commit. The release workflow verifies
its packages before publishing those same artifacts.

No new formal cross-library benchmark ranking is published with 0.2.0. The
[0.1.0 performance record](../performance.md) applies only to its measured revision,
not this dependency-capture architecture. No general fastest or allocation-free claim
is made for all routes and lifetimes.
