# Zendiator 0.4.0

基本の入口は `AddZendiator()` と生成 `IZendiator` のままです。Mediatorの既定はScopedで、依存は初回に遅延取得し、そのMediator内で再利用します。依存の破棄はDIが担います。

## 追加APIと移行時の変更

- `IStreamRequestValidator<TRequest>` と `AddStreamRequestValidator(Type, order)`、または `StreamRequestValidatorAttribute` で、同期のStream入力検証を明示登録できます。対象となる閉じたStream要求に対応する、閉じた具象クラスを登録します。`StreamAsync` の入口で1回検証し、HandlerとBehaviorは列挙時に遅延実行します。[Streamの利用方法](../../README.ja.md#ストリーミング)を参照してください。
- `SendAllSync(request, destination, cancellationToken)` で、呼び出し元の `Span<T>` に順序どおり結果を書けます。3引数すべてが必要です。容量はHandler取得前に検査し、全Handlerの成功後に出力を変更します。生成 `IZendiator` を手動実装している場合は、新しいオーバーロードを追加してください。
- 結果を集める `SendAllAsync` / `SendAllSync` の契約は `IReadOnlyList<T>` のままですが、実体は固定長配列になりました。`List<T>` へのキャストは外してください。
- 生成されるResolverの基底型は構成に応じて変わります。本体とGeneratorの版を揃えて利用側を再コンパイルし、具体的な基底型ではなく生成インターフェースを使ってください。
- Streamの初期化が失敗した列挙器は停止し、以降の `MoveNextAsync` はfalseを返します。破棄した後、`StreamAsync` を呼び直して新しい列挙を開始してください。

## 非同期操作の消費

Streamの開始・破棄やNotificationでは、非同期処理の記録をプールで再利用して繰り返しの確保を減らしました。返された `ValueTask` は1回だけ消費します。同じ操作を複数回待つ場合は、`AsTask()` を1回呼んで得たTaskを再利用し、元のValueTaskは消費しません。通常の `await foreach` と `await using` はこの契約に沿っています。プール化した破棄は、完了後もValueTaskを消費するまで列挙器の参照を保持する場合があります。

送信とStream列挙が終わるまでScopeを維持してください。Scopeの破棄は実行中の処理を取り消したり待ち合わせたりしません。Transient登録の依存も、同じMediator内では捕捉後に再利用します。

## 性能と対応範囲

[READMEの比較](../../README.ja.md#性能比較)は固定ソース版 `1c41d2b` の全360件から、選定に必要な条件を抜粋したものです。初回取得やStreamの不利な例も載せています。各ケース1 launchで、変更前後の因果的な改善や全条件の非劣化は認定しません。

逐次Notification、型付きの要求・Stream、.NET 10という要件は維持しています。Native AOTの検証対象はwin-x64のパッケージ利用です。値型で閉じるopen generic Handlerは既知の制限です。[対応範囲](known-limitations.md)と[MediatRからの移行](../migrating-from-mediatr.ja.md)を参照してください。
