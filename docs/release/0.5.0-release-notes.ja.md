# Zendiator 0.5.0

0.5.0では登録・Handler・StreamのAPIが変わります。0.4.0から更新する際は、
[導入ガイド](../getting-started-0.5.0.ja.md)に沿って移行し、利用側を再コンパイルしてください。
.NET 10とC# 14が必要です。1.0より前のAPIには変更が入る場合があります。

## パッケージ

`Zendiator`と`Zendiator.Abstractions`は同じ版を使います。`Zendiator`にはSource Generatorが
含まれ、Abstractionsへの依存もあります。契約だけを置くプロジェクトではAbstractionsのみを参照できます。

```shell
dotnet add package Zendiator --version 0.5.0
```

NuGet.orgで0.5.0が公開されるまでは、同じ版のローカルビルド済みpackageを使ってください。
任意導入の`Zendiator.CodeFixes`は、同じ版を`PrivateAssets="all"`で別途追加します。
実行時の依存にはなりません。

## 登録と移行

- Handlerに`[ZendiatorHandler]`を付け、`Handlers`で明示的に選びます。名前付き構成には
  `[ZendiatorComposition]`を使います。
- HookとWrapperは順序付きの`Pipeline`で宣言します。型を変更するStreamでは
  `StreamPipeline`で最終要素型も指定します。対象となるHandlerのみのSend経路では空の
  Pipelineを省略できますが、0段Streamでは空のPipelineを明示します。
- 既存Wrapperのretry・cache・継続呼び出しの意味を保持して移行してください。
  任意のWrapper本文を自動でHookへ書き換えるものではありません。
- 0.4.0のStream Handler契約は、`IAsyncEnumerable<T>`を返す`IStreamHandler`、または
  名前付きcursorを開く`IStreamSourceHandler`へ置き換わります。`StreamAsync`は標準の
  非同期列挙を返します。

## 所有と完了

生成登録の既定は`IZendiator`がScoped、Handler・Hook・session factoryがTransientです。
Mediatorは取得した依存を再利用し、Transientも対象です。対象となる非同期Hook経路では、
最初のHookより前にroute単位の依存セットを取得します。外側Hookの失敗で未使用になる依存も
含むため、constructorの実行時期やTransientの同一性がroute間で変わる場合があります。
生成・破棄はDIが所有します。dispatch・列挙・後始末が終わるまでscopeを維持し、
返された`ValueTask`は1回だけ消費してください。

対象となるplain `SendAsync`経路はHandlerの元の`ValueTask`を返します。依存解決や同期callbackは、
操作が返される前の呼び出し中に例外を投げる場合があります。呼び出しとawaitの両方をtry内に
置いてください。内部helperによるambient状態の隔離やUI contextへの復帰は保証しません。

guard付きのStream経路は最初のMoveで入力を取得し、操作の重複を拒否します。
Before・Hook・middleware・owned sessionを持たず、API側と列挙側の両tokenが取消不可の
iterator経路では、`GetAsyncEnumerator`で入力を取得してproducerの契約に従います。
この場合もEOFや失敗後のDisposeAsyncをawaitしてください。`await foreach`を使い、
実際の取消tokenを渡してください。[入力と有効期間のガイド](../streaming-iterators.md)も参照してください。

`StreamSource(...).ConsumeAsync(...)`は逐次処理用の別terminalで、`IAsyncEnumerable`では
ありません。値型sinkはコピーされるため、集計結果は共有する参照型の状態に保持します。
このterminalが常に低時間・低割当量になるとは限りません。

## 依存の保持・診断・IDE修正

閉じた依存の保持領域は既定でinlineです。適した処理では`ClosedServiceCacheMode.LazyBlocks`を
明示的に選べますが、密なアクセスや繰り返し利用では費用が増える場合があります。
open genericの依存には、辞書へ昇格する前の小さなcacheを使います。どちらも全条件での高速化を保証しません。

設定診断は曖昧な登録や未対応の契約を拒否します。診断を抑制しても未対応の経路は有効になりません。
別途追加する任意のCodeFixは、現行Visual StudioでHandler属性の付け忘れを修正し、
現在の文書内のFix Allに対応します。登録順・有効期間・Wrapperの意味は自動で移行しません。

## 性能と制限

[README](../../README.ja.md#性能比較)には、測定対象の0.5.0候補から選んだ利用場面の比較を
掲載しています。同期処理や繰り返し呼び出しで時間・割当量が小さい例がある一方、
新規scope・短絡・途中終了には不利な結果もあります。非同期StreamやRelayでは割当量が
大きくなる場合があり、Behavior 0の非同期Streamと5段の非同期Relayは時間も不利でした。
全条件での優位や、条件を揃えた変更前後の改善を示すものではありません。

Native AOTのpackage利用側検証はwin-x64が対象です。値型で閉じるopen generic DI Handlerには
制限があり、ほかのRIDは未検証です。実行時objectによるrequest・Stream配送と並列Publishは
未対応です。導入前に[既知の制限](known-limitations.md)で、所有・ambient context・参照の保持・
非同期処理の範囲を確認してください。
