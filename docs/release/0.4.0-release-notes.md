# Zendiator 0.4.0

The standard entry remains `AddZendiator()` and the generated `IZendiator`. The default mediator is Scoped; dependencies are resolved lazily and reused within that mediator. DI owns their disposal.

## New APIs and migration

- Synchronous stream input validation is opt-in through `IStreamRequestValidator<TRequest>` and `AddStreamRequestValidator(Type, order)`, or `StreamRequestValidatorAttribute`. Register closed concrete classes for exact closed stream routes. Validation runs once at `StreamAsync` entry; handler and behavior execution remain lazy at enumeration. See [Streaming](../../README.md#streaming).
- `SendAllSync(request, destination, cancellationToken)` writes ordered results into caller-owned `Span<T>`. All three arguments are required. Capacity is checked before handler resolution, and the destination changes only after all handlers succeed. Manual implementations of a generated `IZendiator` need the new overload.
- Collecting `SendAllAsync` / `SendAllSync` still returns `IReadOnlyList<T>`, now backed by a fixed-size array. Remove casts to `List<T>`.
- Generated resolver base types can change with composition. Recompile consumers with matching runtime and generator versions and use the generated interface rather than an exact base type.
- Failed stream startup stops that enumerator; later `MoveNextAsync` returns false. Dispose it, then call `StreamAsync` again for a fresh attempt.

## Asynchronous consumption

Stream startup/disposal and notification dispatch reduce repeated allocation using pooled asynchronous machinery. Consume every returned `ValueTask` once. For repeated waits, call `AsTask()` once and reuse that Task without consuming the original ValueTask. Normal `await foreach` and `await using` already follow this contract. A completed pooled disposal can retain the enumerator until its ValueTask is consumed.

Scopes must remain alive through sends and stream enumeration. Scope disposal does not cancel or join ongoing operations. Captured Transient dependencies are also reused within one mediator.

## Performance and boundaries

[README comparisons](../../README.md#performance) use the fixed `1c41d2b` source snapshot and selected workloads from all 360 cases. They include unfavorable first-use and stream conditions. Each case has one launch; the comparison does not establish a causal before/after gain or universal non-regression.

Sequential notification dispatch, typed request/stream dispatch and .NET 10 requirements are unchanged. Native AOT verification targets package consumers on win-x64; open-generic handlers closed over value types remain a limitation. See [known limitations](known-limitations.md) and the [MediatR migration guide](../migrating-from-mediatr.md).
